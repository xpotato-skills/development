# 日本語リリースノート

ユーザーが「何が良くなったか」「どれを入手するか」「どう更新するか」をすぐ判断できる更新告知を書く。Minecraft Release Changelogs の見渡しやすさを構成の参考にし、固有の文面、ロゴ、装飾、製品の世界観はコピーしない。対象プロジェクト自身の声と用語で、自然で正確な日本語にする。

## 根拠を揃える

- 対象版と比較元を確定し、タグ差分、採用 PR、既存本文、公開 asset、必要な検証記録を確認する。コミット一覧をそのまま貼らず、変更をユーザーが観測する挙動へ言い換える。
- 特に「修正」「新規対応」「高速化」は根拠を確認する。過去から存在する機能を新機能にせず、合成測定を実環境の速度保証に広げない。CI 成功、配布物検証、実機導入、実サービス接続は区別する。
- 根拠のない日付、要件、対応 OS、既知の問題、解決済み判定は補わない。不明点が判断を妨げる場合だけ確認し、書ける範囲を先に仕上げる。
- 公開文面に使える情報だけを採用する。内部履歴、個人の環境情報、非公開 URL、資格情報は公開しない。
- この SKILL 自身の作者・配布ライセンス・謝辞を、生成するリリースノートやユーザー向け出力へ挿入しない。対象ソフトウェア自身の著作権・ライセンス・第三者通知・対応ソース案内は保持する。SKILL の再配布では、配布物に属する LICENSE・NOTICE 等を保持する。手順に不要な配布メタデータは毎回読み込まない。

## 読む順に組み立てる

基本形は [references/template.md](references/template.md) を使い、変更規模に合わせて不要な節を省く。見出しの数を満たすために内容を作らない。

1. 製品名と版、1〜3 文の導入で今回の主な改善と影響を伝える。
2. 最初の画面内を目安にダウンロード導線を置く。OS・アーキテクチャごとの実行用 asset に説明付きの直接リンクを付ける。対応ソース、checksum、署名・出自情報を別用途として明示する。「Assets から選ぶ」だけで終わらせない。
3. ハイライトを短くまとめ、新機能・変更・修正を必要に応じて分類する。一項目は原則一つの挙動。内部名だけの説明は避け、利用者への効果を先に書く。
4. 導入・更新の節で、新規利用者と既存利用者の手順、前提、再起動、移行・互換性への影響を案内する。長い検証コマンドは後半へ置き、入口から案内する。
5. 技術情報、検証範囲、既知の問題・注意事項、ライセンス・第三者通知・対応ソースを必要に応じて続ける。重大な注意事項は導入より前にも示す。

日本語の助詞・主語を補い、直訳調、過剰な宣伝、無意味な英語見出し、作業経緯の羅列を避ける。コード、コマンド、版番号、asset 名、ハッシュ、識別子は正確な原表記を保つ。

## 既存 Release を改稿する

公開本文の編集依頼がある場合だけ、対象 Release の本文を更新する。この SKILL 自体は公開・merge・タグ変更・asset 差し替え・ソフト実行・導入・権限変更の許可を与えない。

- 編集前の本文全体と対象識別子をローカルに保存する。既存の導入手順、固定版・asset ID・digest、検証スクリプト、対応ソース、クレジット、第三者条件、注意事項を点検し、改稿で欠落させない。
- 検証済みコマンドは、説明の整理だけならそのまま保持する。コマンド変更が必要なら変更部分を検証し、未実施の動作を検証済みと記さない。
- 書き込み直前に元本文との一致を再確認する。他者の変更を検出したら再取得して統合する。本文以外の tag、asset、公開状態などは依頼された場合だけ変更する。
- UTF-8 のファイルまたは構造化引数で更新し、読み戻して候補本文と照合する。結果が不明なら再試行より先に現状を確認する。

## 仕上げのチェック

- 版・比較元と変更事実が一致し、各ハイライトを根拠へ辿れるか。
- ダウンロード先は対象版の適切な実行用 asset か。ソース archive と取り違えないか。
- 新規導入、既存更新、検証、起動・停止の順序と前提が明確か。
- 固定値・コマンド・ライセンス・クレジット・第三者通知・ソース提供案内・重要な制約を維持したか。
- 実施済みと未実施を区別し、非公開情報や他製品の文面を混入していないか。
- 対象ソフトウェアの必要な表示を保ち、SKILL 自身の作者・配布条件を出力へ転記していないか。
- 見出し、箇条書き、表、コードブロック、リンク、文字化けを確認したか。

成果として完成本文を示し、更新した場合は Release リンクと読み戻し結果を報告する。未解決の根拠・公開権限・ライセンス選択があれば、その対象と残作業を明示する。
